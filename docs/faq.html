1. actor/grad_norm 持续上涨（推理↔训练精度不匹配）★

症状：训练能跑，但 actor/grad_norm 一路增大，策略不稳定。

排查：打开 rollout 侧 log-prob 对比：

actor_rollout_ref.rollout.calculate_log_probs=True

观察新增指标 training/rollout_probs_diff_mean：

数值含义
< 0.005正常
> 0.01推理引擎与训练侧存在精度差异（不是你的超参问题）

已知触发条件（三条同时满足时高发）：

  1. 非 Hopper 架构 GPU（A100 / L20 / B200 等）
  2. vLLM 存在 issue 22103 的版本
  3. 输入输出较长（多轮 / Qwen3 类推理模型长思维链）

修复：根因是 vLLM 所用 flash attention 的 LSE bug（修复未随 vLLM ≤0.10.2 发布），临时关掉 cascade attention：

+actor_rollout_ref.rollout.engine_kwargs.vllm.disable_cascade_attn=True

2. NCCL hang / 超时

训练挂起不报错或最终 NCCL timeout，九成是并行度约束被违反导致部分 rank 走了不同分支：

  • TP × PP × CP × DP(EP) ≠ 总卡数（trainer.nnodes × n_gpus_per_node）
  • transformer 层数不能被 PP 整除且未手动指定切分（num_layers_in_first/last_pipeline_stage）
  • head 数 / hidden 维度不能被 TP（或 Ulysses SP）整除
  • vLLM rollout 的 expert_parallel_size 不满足 EP=TP×DP
  • ref 的 Megatron 并行度与 actor 不一致（权重同步死锁）

排查技巧：临时调大超时便于抓现场 actor_rollout_ref.nccl_timeout=1800， 然后看各 rank 卡在哪个 collective 上（py-spy / nsight systems）。

3. OOM 系

完整决策路径见显存篇（分阶段画像 + 降级阶梯 + 排查表），此处只列高频误判：

误判实际原因
「util 明明只有 0.5 还是 OOM」CUDA graph 显存不受 gpu_memory_utilization 约束且无法 offload——enforce_eager=True 或缩小 cudagraph_capture_sizes
「micro batch 已经是 1 了还 OOM」峰值由 token 数决定——改用动态 batch（use_dynamic_bsz=True）压 token 预算，或上序列并行
「第一步没事后面才 OOM」长尾样本：最长序列决定峰值；或梯度累积期未分片梯度（use_no_sync_for_gradient_accumulation）
换 SGLang 后按原 util OOM两引擎 util 定义不同（vLLM 按总显存、SGLang 按空闲显存静态部分），数值不能照抄

4. CUDA illegal memory access

rollout 阶段报 CUDA error: an illegal memory access was encountered： 到 vLLM 官方文档 按你所用版本排查 （常见为特定 attention 后端 + 特定 GPU 架构的组合 bug，升级 vLLM 或切换 enforce_eager / attention backend 验证）。

5. Triton compile_module_from_src 报错

堆栈含 triton/runtime/build.py ... compile_module_from_src ... CalledProcessError： Triton JIT 编译 fused kernel 时本机 C 编译环境有问题。 按官方建议关闭 fused kernel 的即时编译： 

actor_rollout_ref.actor.use_torch_compile=False

（代价是损失 torch.compile 的提速；更彻底的解法是修好系统的 gcc/clang。）

6. Ray：注册失败 / 多机 / SLURM / 调试

6.1 "Unable to register worker with raylet"

常见于 SLURM：系统限制了 CPU 共享方式，ray.init() 起的 worker 看不到 raylet。修复：

ray_kwargs.ray_init.num_cpus=<系统允许的核数>

6.2 多机训练

先按 Ray 官方指南起集群（head + worker），再设 trainer.nnodes=<机器数> 提交。 SLURM 用户参考官方 examples/tutorial/slurm/ray_on_slurm.slurm 模板改资源配置后 sbatch。

6.3 分布式断点调试

用 Ray 官方 distributed debugger（debugpy 断点进任意 worker）： docs.ray.io → ray-distributed-debugger

7. train / mini / micro batch 是什么关系？

train_batch_size × rollout.n        ← 一次 RL 迭代采多少样本（算法语义，全局）
   └─ ppo_mini_batch_size            ← 一次 optimizer.step() 用多少（全局）
        └─ micro_batch_size_per_gpu  ← 每卡一次 fwd/bwd 多少（性能参数，本地）
                                        开 use_dynamic_bsz 后由 *max_token_len_per_gpu 取代

官方图解：excalidraw 链接。 详见性能篇 §4。

8. Checkpoint：转 HF 格式 / 断点续训

  • 转 HF safetensors：verl/model_merger（Megatron 分片 → HF 单格式必经步骤）
  • 断点续训：trainer.resume_mode=auto（默认，有 checkpoint 自动续）； 指定路径用 resume_mode=resume_path resume_from_path=...
  • 只存模型不存优化器：actor.checkpoint.save_contents=['model']； 导出 HF 格式加 'hf_model'（分片存储省空间）
  • 滚动清理：trainer.max_actor_ckpt_to_keep=N
  • 大模型 Megatron 路径建议 actor.checkpoint.async_save=True（异步保存不阻塞训练）
