1. 先测量：找到时间都花在哪

RL 一个 step = 生成 + 旧策略 log-prob + ref log-prob + critic/RM 前向 + actor/critic 更新（+ 验证）。 调优前先看 wandb/console 里的 step 时间分解（timing/gen、timing/actor_update 等）， 判断瓶颈在推理侧还是训练侧——两者对策完全不同：

  • 生成占比高（长思维链任务几乎总是如此）→ 先做 rollout 调优或异步化
  • 更新占比高 → 动态 batch + kernel 优化
  • 长尾等待/负载不均 → trainer.balance_batch=True（默认开）按 token 数均衡各 DP rank 的批次

深入分析工具：

工具配置用途
torch profilerglobal_profiler.tool=torch + steps=[s,e]kernel 级火焰图，定位慢 kernel
nsysglobal_profiler.tool=nsysNCCL 通信与计算重叠分析
torch_memoryglobal_profiler.tool=torch_memory显存分配快照 / OOM 现场
Ray timelineray_kwargs.timeline_json_file=...driver 调度与 worker 空闲分析

2. Rollout 吞吐调优（通常是最大头）

官方 perf_tuning 的推荐动作，按性价比排序：

  1. 打开 rollout 统计：rollout.disable_log_stats=False， 观察 GPU cache utilization（KV cache 命中率）与 running/pending 请求数，一切调优以数据为准
  2. 提高 gpu_memory_utilization：KV cache 变大 → 并发更高。 训练侧 offload 全开后可到 0.8–0.9；注意 vLLM（占总显存比例）与 SGLang（占空闲显存中静态部分比例）语义不同
  3. 加大并发窗口：cache 利用率低时调大 max_num_seqs（默认 256）或 max_num_batched_tokens（官方建议 > 2048，经验值 max(8192, max_prompt_length + max_response_length, max_model_len)）； enable_chunked_prefill=True（默认开）配合使用
  4. TP 尽量小：同样卡数下多个小 TP replica（高 DP）吞吐优于大 TP——TP 内每层有 all-reduce， DP 只在数据层面切分；代价是 KV cache 总量变大。TP>8 后收益急剧变差
  5. prefix caching：enable_prefix_caching=True（默认开）对多轮工具调用 / GRPO 同 prompt 采样 n 次的场景收益显著
  6. 采样参数：temperature=1.0 / top_p=1.0 / top_k=-1 保持足够随机性， 也避免了某些引擎的额外分支开销
进阶：① PD 分离（SGLang）：rollout.disaggregation.enabled=True， prefill/decode 独立 replica + nixl/mooncake KV 传输；② 过采样提前终止： rollout.over_sample_rate 让全组提前收工（DAPO 式组内已够好即停）；③ MoE 推理 expert_parallel_size——注意 TP=32 时开 EP 反而可能拖慢 DeepSeek-V3 rollout，务必实测。

3. 序列打包与 remove padding

RL 样本长度方差极大（回答从几十到上万 token），按最长序列 padding 会浪费大量算力。 use_remove_padding=True 启用 THD 打包路径（去 padding、变长拼接），是几乎所有场景的第一优先级开关： 

actor_rollout_ref.model.use_remove_padding=True    # actor + rollout log-prob
critic.model.use_remove_padding=True              # critic（如有）
  • Megatron 后端默认已开（...megatron.use_remove_padding=True）；FSDP 需显式设置
  • 收益与批次内 padding 占比成正比——长尾长度分布下尤其明显
  • 配套：fsdp_config.pad_to_length=True + pad_to_length_bucket（如 1024）， 把打包后的 token 数对齐到少数几个档位，避免每个 micro batch 形状都不同导致 kernel 反复重编译； 设为 max_token_len_per_gpu × SP 可让所有 batch 归一到单一形状
  • 新模型接入建议先跑 pytest -s tests/models/test_transformer.py 验证 padded/unpadded 前向一致

4. Batch size：全局与本地、固定与动态

verl 的核心原则（写进官方文档的归一化规则）：

类型参数视角
算法语义data.train_batch_size、actor.ppo_mini_batch_size、critic.ppo_mini_batch_size全局（单控制器视角），worker 内部自动除以 DP
性能参数*micro_batch_size_per_gpu、*max_token_len_per_gpu每卡本地，直接决定每卡显存与算力批次
注意：脚本里请用 *_per_gpu 版本；旧的 ppo_micro_batch_size（全局）已标记废弃。

4.1 全链路换算公式（源码核实）

归一化发生在 worker 内部（verl/workers/engine_workers.py: train_mini_batch）， 四个量的换算关系（固定 batch 路径）： 

DP（数据并行度）:
  FSDP 后端   = world_size ÷ ulysses_sequence_parallel_size
               （fsdp_size 只影响分片组，不影响数据切分）
  Megatron    = world_size ÷ (TP × PP × CP)      （EP 再从 DP 细分专家）

每 DP rank 样本数 = train_batch_size × rollout.n ÷ DP
mini_batch_per_gpu = ppo_mini_batch_size ÷ DP       ← 必须整除，否则断言失败
梯度累积次数       = mini_batch_per_gpu ÷ ppo_micro_batch_size_per_gpu
每轮 optimizer 步数 = (每 DP rank 样本数 ÷ mini_batch_per_gpu) × ppo_epochs

代入官方 8B 基线（单机 8 卡 FSDP，全分片，ulysses=1 → DP=8）：

train_batch_size=1024, rollout.n=1  → 每 rank 128 个样本
ppo_mini_batch_size=256             → 每 rank 32（整除 ✓）
若 ppo_micro_batch_size_per_gpu=4   → 每次优化 step 累积 8 个 micro-batch
一轮数据 128÷32=4 次优化 step × ppo_epochs(=1)
两个易错点：① ppo_mini_batch_size 不整除 DP 时启动即断言报错（报错信息就是上面源码的 assert）； ② trainer.balance_batch=True（默认开）按 token 数在 DP rank 间均衡，样本数会轻微偏离公式值， 但 mini/micro 的切分仍按上述公式执行。动态 batch 开启后，micro 一层被 token 预算取代，mini 一层公式不变。

4.2 固定 micro batch 的调法

micro 只是 mini 的切分粒度：一次 optimizer step 处理 mini_batch_per_gpu 个样本， 显存装不下就切成若干 micro-batch 做梯度累积。每个 micro-batch 的 fwd/bwd 有固定开销 （kernel 启动、通信往返、算力不满载），切分次数越少越快： 

mini_batch_per_gpu = 32
micro_per_gpu = 4   →  8 次 fwd/bwd + 梯度累积，凑一次 step
micro_per_gpu = 32  →  1 次 fwd/bwd 直接算完，累积次数 = 1（物理上限）
  • 上限是 mini_batch_per_gpu：dataloader 每 step 只给这么多样本，micro 再大也无样本可填， 且源码要求整除（total_data_size % micro_batch_size_per_gpu == 0 断言）
  • 下限受显存约束。完整决策式：ppo_micro_batch_size_per_gpu = min(显存能装下的最大值, mini_batch_per_gpu)
  • 前提：先开 gradient checkpointing——激活显存降一个量级后，「显存能装下的最大值」往往能直接顶到 mini 本身
  • 纯前向角色（ref/rollout 的 log-prob、critic/RM forward）可设为 actor 的 2 倍
  • critic / reward 的 micro batch 可大于 actor（actor 输出头 vocab 巨大是瓶颈）

4.3 动态 batch（推荐）

use_dynamic_bsz=True 后不再调 *micro_batch_size_per_gpu， 改调 token 预算 *max_token_len_per_gpu（详见显存篇 §4.2）。 它同时解决「显存峰值由最长序列决定」和「短序列 batch 算不满」两个问题，官方 8B 基线脚本默认全角色开启。

批次大小本身的语义：train_batch_size 个 prompt × rollout.n 个回答 = 一次迭代的样本数。 gen_batch_size（默认 = train_batch_size）控制每次从 dataloader 取多少 prompt， 分离异步模式下可以 > train_batch_size 攒批。

5. Kernel 级优化：compile、Liger、融合 kernel

手段参数说明
torch.compile actor_rollout_ref.actor.use_torch_compile=True（默认开） FSDP 路径默认启用；配合 pad_to_length 统一形状效果最佳（减少重编译）
LigerKernel actor_rollout_ref.model.use_liger=True 融合 RMSNorm/SwiGLU/RoPE（Triton），SFT 与 RL 均可用；安装 liger-kernel==0.8.4
融合输出头 actor_rollout_ref.model.use_fused_kernels=True log-prob 输出头 chunk 化融合计算（FusedLinearForPPOFunction），直接砍 logits 峰值； Megatron 下可与 use_liger 联用选 Liger 的 TP 版输出头
QAT / 权重量化 actor.qat.*、rollout.quantization.* 实验性，对吞吐和权重同步成本都有影响，需按官方 recipe 使用
Liger × DeepEP 限制：Megatron 原生 Liger 输出头不能与跨节点 DeepEP V1（NVSHMEM RDMA）同进程共存， 需改用 alltoall / DeepEP V2 或关掉融合输出头。

6. FSDP 通信优化

  1. Hybrid Shard：fsdp_config.fsdp_size = 单机 GPU 数，all-gather 限制在机内 NVLink 域，多机时显著提速（见并行篇 §3.1）
  2. 前向预取：fsdp_config.forward_prefetch=True（FSDP1），通信与计算重叠；后向预取官方不支持
  3. 梯度累积免同步：use_no_sync_for_gradient_accumulation=True（FSDP2 路径 set_requires_gradient_sync(False)）， 每 mini-batch 梯度同步从 M 次降到 1 次，数值不变；代价是累积期保留未分片梯度、峰值显存升高——显存紧张时保持默认 false
  4. FSDP2：strategy=fsdp2，DTensor/按参数分片，+1.5% 吞吐（TorchTitan 基准）
  5. reshard_after_forward=false：前向后不重分片（SHARD_GRAD_OP），省一次 all-gather 换显存

7. 异步训练：colocate / separate async

同步（sync）模式下生成与更新串行，GPU 在两个阶段各有一半时间「半闲置」。 trainer.v1.trainer_mode 提供两条异步化路径：

模式机制关键参数
colocate_async 同一批 GPU 上训练与推理交错执行，rollout 数据攒够即训 v1.colocate_async.num_warmup_batches（起步预攒批数，支持小数）
separate_async 独立 rollout 池（rollout.nnodes/n_gpus_per_node > 0），训练 GPU 全速更新 v1.separate_async.num_warmup_batches、parameter_sync_step（每几步同步一次权重）、hybrid_rollout.enable_switch（训练 GPU 闲时借给 rollout）

异步 = off-policy 程度上升，需配合采样控制：v1.sampler.max_off_policy_threshold （轨迹最多跨越多少个模型版本，默认 8；超出按 max_off_policy_strategy drop 或 wait）， 设 null 则完全放开。one-step off-policy 变体见 verl/experimental/one_step_off_policy/。

8. 吞吐 × off-policy 的权衡

几个「加大就更快但更 off-policy」的旋钮，按对稳定性的影响排序：

参数加大后的效果代价
actor.ppo_epochs同一批数据多次更新，rollout 次数减少importance ratio 偏离 1，clip 生效更频繁（默认 1，GRPO 常用 1）
data.train_batch_size单步样本多，rollout 开销摊薄off-policy 漂移增大；mini/micro 批次联动调整
trainer.v1.separate_async.parameter_sync_step权重同步频率降低推理策略滞后于训练策略
v1.sampler.max_off_policy_threshold更多陈旧轨迹可用训练信号失真

经验：先在 sync 模式把单阶段吞吐调到最优，再考虑异步化；异步收益在「生成远慢于更新」的任务上最大。

9. 调优 checklist

  1. ☐ disable_log_stats=False，看 step 时间分解 + KV cache 利用率
  2. ☐ use_remove_padding=True（actor/critic/model）
  3. ☐ use_dynamic_bsz=True + token 预算调到显存上限（前向角色 2×）
  4. ☐ use_torch_compile=True + pad_to_length=True 统一形状
  5. ☐ rollout：gpu_memory_utilization 顶格（配合训练侧 offload）、TP 尽量小、并发窗口够大
  6. ☐ use_liger=True / use_fused_kernels=True（模型支持时）
  7. ☐ 多机 FSDP：试 Hybrid Shard（fsdp_size=单机卡数）+ forward_prefetch
  8. ☐ 显存富余再开 use_no_sync_for_gradient_accumulation=True
  9. ☐ 生成占比仍 > 70%：评估 colocate_async / separate_async
  10. ☐ 每改一项记录一次吞吐（tokens/s 或 step 时间），防止负优化
