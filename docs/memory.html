1. 显存都花在哪：RL 训练的五个阶段

与 SFT 不同，RL 后训练在一个 step 里让 同一批 GPU 轮流扮演不同角色 （hybrid engine 共置模式），每个阶段的显存画像完全不同。OOM 排查的第一步永远是： 确认到底是哪个阶段 OOM——看报错堆栈中的 worker 函数名：

阶段堆栈特征显存大头可控参数
① Rollout 生成 generate_sequences / vLLM、SGLang 内部 推理权重 + KV cache + CUDA graph rollout.gpu_memory_utilization、enforce_eager 等
② 旧策略算 log-prob actor_rollout_ref.rollout ... compute_log_prob 前向激活 + logits（无梯度） rollout.log_prob_micro_batch_size_per_gpu / log_prob_max_token_len_per_gpu
③ Ref 算 log-prob ref ... compute_log_prob 同上 + ref 权重 ref.log_prob_*、ref.*.param_offload
Critic / RM 前向 compute_values / compute_rm_score critic/RM 权重 + 激活 critic.forward_micro_batch_size_per_gpu 等
④ Actor 更新（最常见） update_policy / update_actor 权重 + 梯度 + Adam 状态 + 反向激活 + logits actor.ppo_micro_batch_size_per_gpu / ppo_max_token_len_per_gpu、offload、recompute
⑤ 权重同步 update_weights / broadcast 临时全量权重 buffer rollout.load_format、rollout.layered_summon

2. 显存估算公式

2.1 静态部分（权重 + 梯度 + 优化器状态）

以 P 个参数、bf16 混合精度训练 + Adam 为例（不分片时单副本总量）：

权重      bf16      2P bytes
梯度      bf16      2P bytes
优化器    fp32 master 权重 4P + AdamW 动量 4P + 方差 4P = 12P bytes
─────────────────────────────────────────────
合计 16P bytes

例：7B  → 112 GB   （80G 单卡放不下，必须分片或 offload）
   70B → 1120 GB
   分片后每卡 ≈ 16P / (TP×PP×DP_shard)，再减去 offload 掉的部分
  • FSDP 全分片（fsdp_size=-1）：三类状态均 ÷ world_size
  • Megatron：权重/梯度 ÷ (TP×PP)，优化器状态在 use_distributed_optimizer=True 时 ÷ DP
  • GRPO 无 critic，且 use_kl_loss=False（如 DAPO 配置）时 ref 角色整体不创建，静态显存大幅下降
  • Critic 通常与 actor 同规模（value head 模型），总预算要按「actor + critic 各一份静态显存」计算

2.2 动态部分（激活 + logits）

激活   ≈ micro_batch_tokens × hidden_size × num_layers × k
        k ≈ 10–34 bytes/element（不开 checkpointing）
        开 full recompute 后：每层只存 1 份输入 ≈ 2 bytes/element，降一个数量级
logits ≈ micro_batch_tokens × vocab_size × (2~7) bytes
        2 = 只算 log-prob；再加 fp32 softmax/中间量峰值可达 7
例：Qwen3-8B（vocab=151k）、micro batch 4096 tokens 时
     logits 一项 ≈ 4096 × 151k × 2 ≈ 1.2 GB，峰值路径下 > 4 GB

logits 是 RL 特有的显存杀手（SFT 中交叉熵可 chunk 化，RL 的 log-ratio 计算曾长期全量物化）， 也是「actor 的 micro batch 必须比 critic/RM 小」的根本原因。

3. 静态显存优化：分片与 offload

按「代价从小到大」排序的静态显存手段：

手段参数代价说明
换 FSDP2 actor_rollout_ref.actor.fsdp_config.strategy=fsdp2 几乎无 官方基准：平均省 ~7% 显存、+1.5% 吞吐，Transformer 架构推荐直接用
Megatron 分布式优化器 ...actor.megatron.use_distributed_optimizer=True（默认开） 多一轮 grad all-gather 优化器状态 ÷ DP
激活 offload（FSDP） actor_rollout_ref.model.enable_activation_offload=True D2H/H2D 拷贝 配合 checkpointing 用，可获得更大 micro batch；目前仅 FSDP 后端
优化器状态 offload ...actor.fsdp_config.optimizer_offload=True 或 ...actor.megatron.optimizer_offload=True step 变慢明显 省 12P/分片数。Megatron 还可部分 offload：+...optim.override_optimizer_config.optimizer_offload_fraction=1（DeepSeek 级模型官方建议开）
参数 offload ...actor.fsdp_config.param_offload=True / ...actor.megatron.param_offload=True 每次 forward 前 H2D 搬回 省 2P/分片数。Megatron 版本还会在 actor 空闲期释放梯度 buffer。ref 权重建议与 actor 同步开启
FSDP2 offload_policy ...actor.fsdp_config.offload_policy=true 中等 FSDP2 专用：训练期间 param/grad/optimizer 三态动态 offload
QAT / 低精度 ...actor.qat.enable=true（w4a16）或 rollout quantization.* 数值风险 实验性，权重 4bit 化
offload 与 rollout 的联动：训练侧 param/optimizer offload 全开之后， rollout.gpu_memory_utilization 才能从 0.5–0.6 提到 0.8–0.9。 只调一边都可能 OOM 或浪费显存。

4. 激活与 logits：checkpointing 与动态 batch

4.1 梯度检查点

  • FSDP：actor_rollout_ref.model.enable_gradient_checkpointing=True（critic 同：critic.model.enable_gradient_checkpointing=True）
  • Megatron：+...actor.megatron.override_transformer_config.recompute_granularity=full recompute_method=uniform； 默认 recompute_modules=["core_attn"] 为选择性重计算（性能干扰最小），全量重计算更省显存但慢 ~30%

4.2 micro batch 与动态 batch

固定 micro batch 按样本数切：actor.ppo_micro_batch_size_per_gpu；由于 RL 样本长度差异极大 （长思维链 vs 短回答），固定样本数会导致实际 token 数波动 → 显存时紧时松。 动态 batch（序列打包）按 token 预算切，是既省显存又提吞吐的首选： 

actor_rollout_ref.actor.use_dynamic_bsz=True
actor_rollout_ref.actor.ppo_max_token_len_per_gpu=24576      # 官方 8B 基线值
actor_rollout_ref.rollout.log_prob_use_dynamic_bsz=True
actor_rollout_ref.rollout.log_prob_max_token_len_per_gpu=24576
actor_rollout_ref.ref.log_prob_use_dynamic_bsz=True
actor_rollout_ref.ref.log_prob_max_token_len_per_gpu=24576

token 预算经验值（来自官方 perf_tuning）：

  • actor 的 ppo_max_token_len_per_gpu：≥ 2×(max_prompt_length + max_response_length)，尽量调大
  • 仅前向的角色（rollout/ref 的 log-prob、critic/RM forward）可设为 actor 的 2 倍
  • 长序列（> 32k）训练：预算相应除以 SP/CP 并行度，逐级下调避免 OOM

4.3 entropy / logits 分块计算

compute_entropy_from_logits 的峰值显存 ≈ tokens × vocab × 7 bytes，两个专用开关：

  • ...actor.entropy_from_logits_with_chunking=True（chunk 默认 2048 行）——前向按块算 entropy
  • ...actor.entropy_checkpointing=True——训练时对 entropy 计算做重计算（常规 checkpointing 不覆盖此处）

仅 entropy_coeff > 0（需要 entropy 项）时相关；GRPO/DAPO 常用 entropy_coeff=0 可完全绕开。

5. Rollout 侧显存控制

参数默认作用
rollout.gpu_memory_utilization0.5推理引擎总预算。vLLM ≥0.7 按总显存比例；SGLang 按空闲显存中静态部分的比例（语义不同，换引擎别照抄数值）
rollout.free_cache_engineTrue生成结束后释放 KV cache——hybrid 模式下训练阶段显存的来源，保持开启
rollout.enforce_eagerFalseTrue = 关 CUDA graph。CUDA graph 显存不受 gpu_memory_utilization 约束、且训练阶段无法 offload，是「明明 util 只有 0.5 还是 OOM」的常见原因
rollout.cudagraph_capture_sizesnull保留 CUDA graph 但只捕获小 batch（如 [1,2,4,8,16,32]），介于性能与显存之间
rollout.load_formatdummy权重同步方式；超大模型可 safetensors（配 data.use_shm=True）
rollout.layered_summonFalse分层 summon 权重，防同步阶段 OOM，代价是更慢
rollout.multi_stage_wake_upFalseSGLang 专用：多阶段唤醒，降低「训练→推理」切换的显存峰值
rollout.max_num_batched_tokens / max_model_len8192 / nullchunked prefill 开启时二者直接决定 prefill 激活峰值

Sleep/wake 机制：verl 在训练阶段把推理引擎权重 offload 出去、生成阶段再唤醒。 若推理引擎残留显存导致训练 OOM，优先检查 enforce_eager/free_cache_engine， 其次降低 gpu_memory_utilization。

6. OOM 降级阶梯（推荐顺序）

遇到 OOM 时按代价从低到高逐级尝试，每改一项重新测一次峰值（不要一次全开）：

  1. 缩小动态 batch 预算：ppo_max_token_len_per_gpu / log_prob_max_token_len_per_gpu 减半（吞吐损失通常最小）
  2. 开 gradient checkpointing（若尚未开）：往往还能换回更大的 micro batch
  3. entropy 分块：entropy_from_logits_with_chunking=True（若用 entropy）
  4. rollout 侧：gpu_memory_utilization 降 0.1 或 enforce_eager=True
  5. offload：先 optimizer_offload，再 param_offload（ref 同步开）
  6. 提高并行分片度：加 TP/PP（Megatron）或降低 fsdp_size（FSDP）
  7. 序列并行：长序列场景上 ulysses SP / CP
测量工具：开启 global_profiler.tool=torch_memory，OOM 时自动 dump 内存快照 （分配栈、各 tensor 大小），比盲猜高效得多。日常监控看 wandb 的 actor/optimizer/memory_allocated 等曲线的峰值而非均值。

7. 分阶段 OOM 排查表

现象首先检查其次
生成阶段 OOM（vLLM 报 CUDA OOM） gpu_memory_utilization 过高 / 模型放不下 → 升 rollout TP max_model_len 过大；chunked prefill 的 max_num_batched_tokens
log_prob 阶段 OOM log_prob_micro_batch_size_per_gpu 或 log_prob_max_token_len_per_gpu 该阶段是纯前向，预算可以是 actor 的 2 倍——反而要防止设小了拖慢
update_policy 阶段 OOM 动态 batch 预算 / checkpointing offload；若手动设过 fsdp_config.use_no_sync_for_gradient_accumulation=true（省通信但会在累积期保留未分片梯度、抬高峰值），改回 false
训练开始没事，几个 step 后 OOM 最长样本是长尾分布 → 峰值由最长序列决定，动态 batch 已缓解；仍 OOM 则降预算 内存泄漏类问题用 torch_memory profiler 抓快照
权重同步阶段 OOM rollout.layered_summon=True load_format=safetensors + data.use_shm=True
NCCL 超时而非 OOM 并行度约束被违反（world 不整除、层数不整除）导致部分 rank 挂起 检查 TP×PP×CP×DP 与层数整除；必要时调大 actor_rollout_ref.nccl_timeout 便于抓现场
